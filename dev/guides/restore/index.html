    Restore and undo¶

    A restore replaces the instance's database and filestore in place:

    apiVersion: odoo.abugharbia.com/v1
kind: OdooRestore
metadata:
  name: back-to-friday
  namespace: shop
spec:
  odooDeployment: my-odoo
  backup: my-odoo-2026-10-17        # or snapshotID: <id> in the instance's store
  keepPrevious: 72h                 # default spec.backup.restore.keepPrevious (72h)

    Odoo is stopped; the backup is loaded into <db>_restore_<suffix> and filestore/<db>_restore_<suffix> beside the live data and checked: every table's row count must match the backup and every attachment the backup holds must be there. A sample of files is also compared with its checksum; a mismatch only adds a warning to status.warnings, as those files were damaged before the backup. Only then are the names swapped: the live data becomes <db>_prev_<suffix> and the restored data takes its place, and Odoo starts on the image recorded in the backup. A restore that fails before the swap leaves the live data untouched (Failed); one that fails during the swap is retried until it finishes, with Odoo stopped and the instance Degraded (RestoreIncomplete). Only the Job's main container swaps: a Job whose pods never got past the steps before it (the load step was OOMKilled, the Odoo step's image could not be pulled) fails with the live data untouched and the step named in status.message. A restore takes precedence over everything else and replaces a failed init or upgrade Job, which makes it the way back from a failed upgrade. Modules in spec.modules that the backup lacks are installed again afterwards. The restore Job lists them in its result; when they are too many for it (Kubernetes keeps 4096 bytes of a Job's result, room for some 250 module names), the result says so instead of listing part of them, and the operator reads the installed modules from the restored database itself, with the instance's database credentials, before Odoo starts on it.

    The instance then counts as running the backup's image and upgrade token. If spec.image differs from the backup's image, the usual upgrade follows when spec.upgrade.onImageChange is true; if spec.upgrade.token differs from the backup's, an upgrade follows either way. Set both to the backup's values first to stay on it.

    A restore by backup falls back to a copy in another store when the backup's store is not ready. A restore by snapshotID reads only the first store in spec.backup.stores.

    Restore a backup from elsewhere¶

    from restores a backup that is not one of the instance's own OdooBackups: a backup file made by Odoo's database manager, or a snapshot in any restic repository the operator wrote, such as another instance's. It names an OdooBackupStore in the same namespace and a path in it; the store does not have to be in spec.backup.stores, and is best made readOnly:

    spec:
  odooDeployment: my-odoo
  from:
    store: imports
    path: exports/shop_*.zip       # a .zip or .dump file; the last segment may be a pattern
  neutralize: true                 # for a copy of production, see below
    path Restores
    ends in .zip Odoo's zip backup: dump.sql, manifest.json and the filestore/ folder, at the top of the zip or one folder down (a backup someone zipped again)
    ends in .dump Odoo's dump backup (pg_dump custom format). It holds no filestore: the instance starts without attachment files, and the restore says so in status.warnings
    anything else the restic repository in that folder, such as prod/my-odoo for the instance my-odoo in namespace prod; empty is the instance's own

    A file's last path segment may be a pattern (*, ?, [a-z]): the match whose name sorts last is restored, the newest for dated names such as shop_2026-10-01.zip. status.file records the file that was picked.

    In a restic repository, snapshot picks a snapshot by ID; without it the newest snapshot is restored, narrowed by host (<namespace>/<name> for the operator's snapshots) and tags (all must match, such as kind=manual). status.snapshotID records the snapshot that was restored. The store's encryptionKeySecret must be the key of that repository.

    A backup from elsewhere records no image, so the instance's own Odoo image checks it: before the swap, Odoo reports its version, and a backup of another Odoo series (17.0 on an 18.0 image) is refused with the live data untouched. Afterwards the instance counts as running spec.image and spec.upgrade.token, so no upgrade follows: set upgrade: true when the backup was made by other code than spec.image holds. A backup the operator made (a restic snapshot) still records its image and token, and is handled like the instance's own backups.

    The checks use what the backup carries. Every attachment the restored database lists must be in the restored filestore, and a sample is compared with its checksum, as for the instance's own backups. Row counts are compared only when the backup recorded them, which Odoo's own backups do not. A zip without a manifest.json restores with a warning.

    Neutralize a copy¶

    neutralize: true makes the restored data safe to run beside production before Odoo first starts on it: Odoo's own odoo neutralize turns off outgoing mail servers, scheduled actions, payment providers and the other integrations each module marks, and the database gets a new database.uuid, so it does not claim production's subscription or IAP credits. The restore fails, with the live data untouched, when Odoo cannot neutralize the database. Neutralize needs Odoo 16 or later, and cannot be set on an undo.

    Upgrade the restored data¶

    upgrade: true upgrades the restored database to spec.image before it is swapped in: the instance's Odoo runs -u with spec.upgrade.modules (all modules when that is empty) on the loaded database and its filestore, after neutralize when that is set too.

    spec:
  odooDeployment: staging
  from:
    store: production-files
    path: shop_*.zip
  neutralize: true
  upgrade: true                    # the backup's modules are older than spec.image's

    Use it when the backup was made by other code than the instance runs: a production backup restored onto an instance that runs a newer version of the same modules, such as a staging or review copy of a branch. Without it, the database keeps the module versions of the backup until the next upgrade.

    • The instance's Odoo must be the backup's series, as for any backup from elsewhere; upgrade moves modules forward within a series, not across one.
    • The restore fails, with the live data untouched, when the upgrade fails; status.message ends with the end of Odoo's log.
    • Afterwards the instance counts as running spec.image and spec.upgrade.token as they were when the restore Job was made, so no upgrade Job follows. status.upgradeToken records that token; the agent reports it from the pod that ran the upgrade. A token changed while the restore ran (or spec.image changed, with onImageChange) is applied next, by the usual upgrade, and status.message says so.
    • upgrade cannot be set on an undo. The upgrade runs inside the restore Job, so the Job's deadline (spec.backup.activeDeadlineSeconds) covers it too.

    What a restore needs¶

    • Room: the restored files sit beside the live ones on the data volume until the swap, so it needs free space for a second filestore, and the database server holds two to three copies of the database for a while (live, restored, and the previous one kept for undo).
    • Database privileges: a restore always creates and renames databases, whatever spec.database.createPolicy says, so the database user needs CREATEDB.
    • Users: the restore Job's steps run with the instance's podSecurityContext. Without runAsUser there, the operator's steps and Odoo's run as their images' own users, so the restored filestore is made writable by the pod's group: folders 2775, files 0664. Set fsGroup (the default does) so that group is one Odoo is in.
    • Downtime: Odoo is stopped from the start of the restore to the end of the swap. With a ReadWriteOncePod data volume it is stopped again, briefly, when the kept data is deleted after keepPrevious.

    What happens if something goes wrong¶

    The live data is never edited in place, so a restore can fail without damaging it, and a Job that dies halfway finishes when it is retried.

    A restore Job runs up to three pods (backoffLimit: 2) for failures that a new pod may get past: a pod killed out of memory, evicted, or one that lost its connection to the database. A failure no new pod can change ends the Job at its first pod instead, through the Job's pod failure policy: the backup refused by its checks (another Odoo series, row counts or attachments that do not match, a file that is not an Odoo backup), odoo neutralize or the upgrade failing, or an undo whose previous data is gone. The agent reports such a failure with exit code 3 and "final": true in its result, and the restore fails with the live data untouched, instead of loading the backup twice more with Odoo stopped. On a cluster that has the Job pod failure policy turned off (it is on by default from Kubernetes 1.26), such a Job simply fails the same way three times. A new pod of the same Job does not run neutralize or the upgrade again when an earlier pod already did, as the restore journal records; should it run either again all the same, its outcome counts, and a database whose latest neutralize or upgrade failed is never swapped in.

    How the operator tells which side of the swap a failed Job ended on:

    • It reads the result of the Job's newest pod only, its latest attempt. An older attempt's result is stale once another pod ran after it.
    • When that pod left a result, the result says whether the swap had started (the agent reads it from the restore journal on the data volume).
    • When it left none, and no pod of the Job got as far as the main container, nothing was swapped: the restore fails, and the message names the step that failed and why (for example failed in step load: OOMKilled (exit code 137)).
    • While the Job's pod cannot start (it cannot be scheduled, a Secret it names is missing, its image cannot be pulled, or it waits for a volume attached to another node), status.message and the instance's Degraded condition (JobCannotStart) say why. When no pod of the Job has started a container 15 minutes after the Job started, the operator deletes the Job, and the restore fails with the live data untouched and Odoo back, rather than keeping Odoo stopped until spec.backup.activeDeadlineSeconds.
    • When it left none after the main container started, or the pods that would tell are gone, the swap may have started: Odoo stays stopped and the restore is retried (status.liveChanged, status.liveChangeUnconfirmed). If the next attempt reports, from the journal, that the swap never started, the restore fails with the live data untouched instead of being retried for ever. A swap that a result reported as started is always finished.

    How a started swap is finished: the retry runs the Job in a mode that only finishes the swap (odoo-backup restore --finish-swap, or undo --finish-swap), a single container reading the restore journal on the data volume. It needs neither the backup nor its store, so it goes on even when the OdooBackup, the store or its Secret was deleted meanwhile, or spec.backup.stores changed. When only an attempt without a result made the swap look started, the retry runs the whole restore again while its source can still be found, and otherwise the finishing mode; that mode changes nothing when the journal shows the swap never started, and the restore then fails with the live data untouched (nothing to finish: the restore journal shows the swap has not started).

    flowchart TD
  start([OdooRestore: Odoo is stopped]) --> load["Load the backup beside the live data:<br/>database db_restore_suffix, its filestore"]
  load --> check[Check row counts, attachments<br/>and a sample of checksums]
  load -->|error| failed([Failed: live data untouched])
  check -->|row counts differ or<br/>attachments missing| failed
  check --> odoo{"from, neutralize<br/>or upgrade?"}
  odoo -- "no" --> swap
  odoo -- "yes" --> step["The instance's Odoo reports its version,<br/>neutralizes and upgrades the loaded database<br/>when asked"]

  step --> swap["Swap: live becomes db_prev_suffix,<br/>restored becomes db"]

  retry --> swap

  kept -->|keptUntil passes| gone([Previous data deleted])

    Undo a restore¶

    The replaced data is kept until status.previous.keptUntil, then deleted. Until then the restore can be undone:

    spec:
  odooDeployment: my-odoo
  undo: back-to-friday

    Only the latest restore can be undone. Deleting an OdooRestore deletes the data it kept.

    Deleting the instance

    Deleting an OdooDeployment whose database is dropped (spec.database.deletionPolicy: Delete) drops the <db>_prev_<suffix> and <db>_restore_<suffix> databases of its restores with it, and deletes their folders from a filestore volume that is kept. With Retain they stay, beside the database.
